用户报告烧录后仍出现旧启动流程。本次检查发现：

- 磁盘上的 `Src/main.c` 又包含色块完成后固定等待 5 秒、再自动显示 UID 的代码。
- `build/Debug/epaper_NFC.hex` 当时的 SHA256 为 `171359fdd153b1b331d22324e6f30fb5a56884f1e40bec370d9fcb3e5d338c96`，与此前导出的新流程 HEX 不一致。
- VS Code F5 和下载任务使用 `build/Debug/epaper_NFC.elf`，因此重新编译旧源码就会再次生成旧启动流程。
- 旧源码快照保存在 `main_before_startup_restore_2026-11-14.c.txt`。恢复前，已有行为测试失败 7 项；恢复后通过。具体由哪个保存操作覆盖源码尚未确认。

本次恢复为：上电/复位显示一次六色色块，随后等待新的有效 NFC 指令；操作码 6 显示 1234。取消自动 UID 画面和启动固定等待，保留两次刷新之间至少 5 秒的休息时间。

版本标识为 `colors-wait-nfc-1234-r2`，可通过调试变量 `g_debug.firmware_id` 查看。构建脚本现在先运行行为测试，失败则停止构建；成功后导出当前 ELF/HEX/BIN 及 SHA256 清单，避免手工导出文件过期。

Debug 和 Release 均已编译、链接并通过 Cortex-M0+ 仿真测试。Debug Flash 35,960 B，Release Flash 33,524 B，链接器 RAM 占用均为 2,144 B。Debug 构建目录、版本化导出目录和通用导出 HEX 的 SHA256 一致：`2744c6e88b975b9214882c651a23a5c3c00410f097436badec8bd064c0690e10`。

本次没有下载到板子，未进行 r2 实板验收。测试不模拟电源和 RF。

如编辑器仍打开修改前的 main.c 内容，请先关闭该标签页，提示保存时选择不保存，再重新从磁盘打开，避免旧缓冲区再次覆盖源码。烧录 `output/firmware/Debug/epaper_NFC_colors_wait_nfc_1234_r2.hex`，或运行已配置构建前任务的 F5。

ST25 NFC Tap 单字节写入（十进制），依次：地址 64 写 0、65 写 6、66 写 9、67 写 170、64 写 165。对应 `A5 06 09 AA`。启动时 EEPROM 内已有的指令不会重放；如果启动前已经是序号 9，改用序号 10（地址 66 写 10、67 写 169），其他步骤不变。
