# NFC 0% / Tag was lost 排查与 APP 1.2 修正

## 本次实际信息

- 用户反馈：一加手机，发现标签会震动；传输始终 0%，随后 Tag was lost。
- 板子外接稳定 3.3V。
- 同一手机曾通过 ST 官方 APP 完成图像文件传输。
- 当前没有 ADB 连接的手机，无法读取此次实际 RF 失败的 Logcat。
- 因此应优先检查本 APP 的 RF 命令实现；不能仅凭异常就认定 MCU 固件故障，也不能把震动视为 Mailbox 握手成功。

## 发现的问题与修正

1. APP 1.1 的 A0 / AD / AE / AA / AB / AC 全部用 flags=22、带 UID 的寻址命令。
2. ST 官方讨论指出：主机通过 I²C 访问 Mailbox 时，标签可能无法读取 UID 来判断寻址命令，建议 Mailbox 使用非寻址命令。
3. 本板软件 I²C 每半周期约 5µs，读取 240 字节约需 22ms，加上 10ms 主循环周期。原 APP 写包后立即按 12ms 间隔发送带 UID 的 AD，存在与 I²C 操作重叠的机会。
4. 1.2 将本应用使用的 ST 自定义配置 / Mailbox 命令改为 flags=02，不附带 UID；写包后等 40ms，再按 20ms 间隔检查状态。传输时只贴近当前这一块 NFC 板。
5. 仍按 Android 发现的 UID 校验目标型号；不修改 EEPROM、密码和锁定位。RF 包长按“flags + command + ST code + length”完整开销检查。
6. 只对 A0 / AD / AB 的明确 0F 错误响应做最多 3 次有限重试；遇到 TagLost / I/O 异常不盲目重发 AA 或 AC，防止重复写和吞掉确认。
7. 报错保留阶段、最后命令 / flags / TX 长度、最后 MB_CTRL、已确认字节数、MCU 握手结果，同时记录 EpaperNfc Logcat。

**这些是可验证的实现修正与诊断补充。本次手机失败的确切命令尚未被捕获，不能把软件测试通过写成手机故障已复现或已解决。**

## 使用新版确认

1. 覆盖安装 app/build/outputs/apk/debug/app-debug.apk，版本 1.2 / versionCode 3。
2. 保留板上原有已用 ST APP 验证的固件与外接 3.3V，无需烧录或修改 NFC 静态配置。
3. 等待 MCU 初始化完成（若当前固件有启动刷屏，等其结束）。APP 内重新选图、手动抖动，点击发送后再贴近。
4. 若成功：可确认原 APP 的 RF 交互路径存在兼容性问题，本次修改在该手机上有效。
5. 若失败：保留整个报错弹窗中的“阶段 / 最后命令 / MB_CTRL / MCU 握手”文本；不要只记录 Tag was lost。

## 如何区分后续问题

| 失败证据 | 判断范围 |
| --- | --- |
| A0 配置读取就无 RF 响应 | 尚未发送 STM32 图像握手，优先检查手机与 ST25DV 的 RF 命令交互 |
| A0 成功，但 MB_MODE=0 | ST25DV 未完成 FTM 配置；检查 MCU 是否启动并运行兼容固件 |
| AA 写入成功，AD 一直返回 05，6 秒内无变化 | RF 数据仍待 I²C 主机读取；检查 MCU 是否仍在刷屏、GPO 事件和 I²C 接收 |
| MCU 握手成功，后续图像包失败 | MCU 已实际响应协议；结合失败命令、包长和段号检查 RF / 数据传输 |
| 段确认成功但最终应用确认失败 | 检查 E6IM 整图验证及最后回执，不能把发送完字节当作刷新完成 |

0% 表示尚无“完整段 CRC 确认”，并不表示已经证明连第一条 RF 命令都没发出去。

## 验证

- APP Debug 构建与 Android Lint 任务通过（项目原有依赖警告仍可能存在）。
- 14 项 JVM 测试通过，0 失败 / 0 跳过。
- 新增 RF 黄金帧、模拟 I²C 仲裁导致的寻址无响应、有限忙重试、不盲重发写入 / 消费性读取、完整 RF 包长边界测试。
- 手机实测仍待用户在一加上重试。此版本未更改生产固件。
