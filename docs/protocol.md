# 图像与 NFC 协议

## E6IM 图片文件

文件大小固定为 28,832 字节：32 字节头部与 28,800 字节像素。

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 4 | ASCII `E6IM` |
| 4 | 1 | 版本，1 |
| 5 | 1 | 像素格式，1 |
| 6 | 2 | 头部长度，32 |
| 8 | 2 | 宽度，240 |
| 10 | 2 | 高度，240 |
| 12 | 4 | 像素字节数，28800 |
| 16 | 4 | 图片 ID |
| 20 | 4 | 像素 CRC32 |
| 24 | 4 | 保留标志，0 |
| 28 | 4 | 前 28 字节的 CRC32 |

头部多字节字段均为小端。CRC 使用 IEEE CRC32：多项式 `0xEDB88320`，初值与最终异或值均为 `0xFFFFFFFF`。

像素按行存放，每像素 4 位，左像素位于字节高半部。颜色编码：0 黑、1 白、2 黄、3 红、5 蓝、6 绿；4 和大于 6 的值无效。

## Mailbox

APP 使用 NFC-V 高数据率非寻址命令，flags=`02`、ST manufacturer code=`02`。同一时刻只将目标板放在手机天线附近。

| RF 命令 | 用途 |
|---|---|
| A0 | 读取静态配置 |
| AD / AE | 读取 / 写入动态配置 |
| AA | 写入 Mailbox 消息 |
| AB / AC | 读取 Mailbox 长度 / 消息 |

RF 侧 `MB_CTRL_Dyn` 地址为 `0D`，I²C 侧为 `2006`。I²C 用户区地址为 `53`，系统区为 `57`，消息缓冲区起始地址为 `2008`。

MCU 使用 PB3 GPO 下降沿事件处理 RF 消息写入和读取完成，GPO 配置为 `B0`。空闲不轮询 I²C；事件发生后为 RF 交接预留时间，并执行有界重试。

RF/I²C 仲裁可能返回明确的 `01 0F` 拒绝。APP 对该响应最多尝试 12 次，退避为 20、40、60、80ms，后续上限 80ms。响应丢失、空响应、TagLost 和其他错误不会盲目重复写包。

每次写包前检查 Mailbox 可写状态。写包后的交接等待从 50ms 开始：连续 8 次普通包交接无需额外等待或忙重试时减少 5ms，最低 20ms；检测到等待或忙重试则增加 10ms，最高 80ms。段确认读取后的 MCU 交接单独等待 30ms，不参与普通包速度反馈。启动供电等待、段校验和刷新完成回执机制保持独立。Logcat 的 `EpaperNfc` 记录上传耗时、屏幕刷新耗时和忙重试次数，供实体手机对比。

## FTM 分包

每段最多 2048 字节。包使用显式 payload 长度，总长度字段为大端，段 ID 交替；段末携带大端 IEEE CRC32。APP 根据手机 `maxTransceiveLength` 扣除 RF 命令开销，单个 FTM 包不超过 240 字节。

段响应 `80` 表示接受，`81` 表示需要重传该段，`83` 表示拒绝。只有完整段被接受后才推进已确认字节数。

## 应用命令

| payload | 用途 |
|---|---|
| `00` | 查询接收器能力 |
| `09` + E6IM 文件 | 上传图片并等待刷屏完成 |

查询响应中的 capability bit0 表示支持刷新完成回执。APP 在发送图片前检查该能力。

图片校验成功后，MCU 返回 `40 02 89 81`。APP 读取该回执后，MCU 才调度屏幕刷新。此时手机显示“正在刷新屏幕”，继续维持 NFC 连接。

## 刷新结果

屏幕驱动完成 BUSY 检查、关电及休眠后，MCU 返回 24 字节结果：

```text
40 16 89 status image_id[4] pixel_crc32[4] elapsed_ms[4] error[4] reset_flags[4]
```

`status=90` 为成功，`91` 为驱动失败；后续五个字段均为小端，`error` 为有符号 32 位数。APP 核对图片 ID 和像素 CRC，只有本张图片的成功结果才能触发“刷新完成”。

`reset_flags` 为 MCU 本次启动时的 RCC_CSR 快照。BUSY 刷新空闲需连续稳定 200ms，关电空闲需稳定 50ms；异常短于 1000ms 的全彩刷新返回错误。APP 最长等待结果 330 秒。

连接关闭、复位、驱动失败或等待超时不会自动重传图像。图片仅存在 RAM；重新上电后，屏幕保持 RESET，等待新的完整图片。
